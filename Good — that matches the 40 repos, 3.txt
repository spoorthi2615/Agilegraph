## ⚠️ Deviations the team already documented (in `research/status-and-limitations.md`)

The repo itself contains an honest "what changed since the synopsis" file. Worth knowing these exist, since a reviewer who only reads the synopsis PDF won't know about them:

1. **Corpus size**: synopsis says 8–10 repos; actual is 40 (upgrade, but a claim mismatch if you present the original PDF as-is).
2. **CBOMkit baseline**: synopsis promises a direct CBOMkit comparison. In practice, CBOMkit-theia is scoped for certs/manifests, not source code — so on source-code nodes it degenerates into a majority-class predictor. It's now marked **N/A** rather than a real comparison point. This means one whole bullet in your "Objectives" and "Expected Outcomes" (benchmarking against CBOMkit) is **not actually fulfilled** as written.
3. **Expert validation (§5.2)** — this is the biggest gap. The synopsis's core evaluation claim (150–200 assets, ≥4 real human security experts, Fleiss' kappa reliability ceiling) is **not done**. The ground truth currently used for the headline 0.913 F1 is generated by **deterministic AST/regex pattern matching**, not human annotation. The doc explicitly calls this "scheduled as the final concluding phase" — i.e., still to-do.
4. Two bugs fixed post-hoc but worth knowing were ever there: a **CBOMkit circularity bug** (baseline was silently re-deriving from the same labeler used for training labels) and a **train/validation leakage bug** (validation repos not guaranteed disjoint from training repos in a fold).

## 🔴 Errors/inconsistencies I found that aren't yet flagged anywhere

1. **Metric drift across documents, only partially reconciled.** `ablation-study.md`/`benchmark-study.md` report Full Model F1 = **0.913** (bootstrapped). `statistical-analysis.md` reports **0.859 ± 0.049** (raw 5-fold). A `METRIC_CONVENTIONS.md` exists to explain this — but it means **any reader who copies "the F1 score" from two different files in your own repo will get two different numbers**, and a panel member cross-referencing your appendix could flag this as inconsistent reporting if the convention note isn't front-and-center in the actual paper/PPT.
2. **Fabricated hardware claim, since removed but worth knowing it happened.** `performance-evaluation.md` states outright: *"The original hardware profile (Intel Xeon Platinum / NVIDIA A100) listed in previous iterations was fabricated and has been removed."* That's a serious thing to have had in a research artifact at all, even if since corrected.
3. **Latency claims contradict the underlying data.** `threats-to-validity.md` claims reproducibility of "~30–40ms inference" and `benchmark-study.md`'s table has an "Inference (ms/repo)" column — but the actual `research/results.json` has **empty `Latency`/`Throughput` arrays**, and `performance-evaluation.md` itself says throughput/latency numbers are still "theoretical until tested on production infrastructure." So you have one document asserting a specific reproducible number and two other artifacts (the raw data file and another doc) saying that number doesn't exist yet. This is an internal contradiction you should fix before a defense — pick one story.
4. **The live/deployed demo does not run your actual model.** Per `deployment/railway-limitations.md`, the deployed instance intentionally **excludes torch/PyTorch Geometric/CodeBERT** (RAM limits), and every scan silently falls back to the plain heuristic scorer — the GATv2+CodeBERT pipeline (your central technical contribution) never executes there. If an examiner tests the live URL rather than running locally, they will only ever see the heuristic baseline, not the GNN. This is fine as an engineering tradeoff, but it's not mentioned anywhere in the synopsis and could look bad if not disclosed proactively during a demo.
5. **"Measurement bias: Mitigated"** in `threats-to-validity.md` is worded to imply objectivity ("ground-truth node labels were generated using strict NIST PQC migration guidelines") but doesn't disclose in the same breath that this is regex/AST-derived labeling standing in for the human-expert labels the synopsis promised — the wording there is more reassuring than the actual state of §5.2 warrants.
6. **Objectives bullet 3** ("benchmarking... against ... an existing open cryptographic-inventory tool (CBOMkit)") and **Expected Outcomes bullet 3** (same claim) are, as written in the PDF, **not satisfied** — the repo's own doc admits the comparison is apples-to-oranges and was dropped in favor of self-ablation only.

## Bottom line
Nothing here looks like empty scaffolding — the code is real and mostly functions as designed. The actual risk for your defense is **presentation-vs-reality drift**: the synopsis (as a static PDF) still promises human expert validation and a CBOMkit benchmark that the current implementation does not deliver, and there's one live self-contradiction (the "~30-40ms" latency claim vs. the empty performance data) that a sharp panelist would catch in five minutes if they read `research/` end to end. I'd fix #3 and #6 before any viva, and be ready to proactively explain #4 (Railway falls back to heuristics) rather than have it discovered live.
